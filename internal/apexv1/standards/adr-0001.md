# ADR-0001: Record architecture decisions

Status: accepted
Date: 2026-10-19

## Context

A project makes choices that bind later work: a language or framework, a dependency and its pinned
version, a storage engine, a protocol, a public format, a convention every change must follow.
When such a choice lives only in someone's memory or in a commit message, later work cannot tell
whether it still holds, and a model planning a change cannot follow it. The project needs one place
where each binding choice is written once, with its reasons, and one way to change it.

## Decision

- Every binding choice is an architecture decision record (ADR) in `development/decisions/`, one
  file per decision, named `NNNN-<slug>.md`, numbered in order. This record is ADR-0001.
- An ADR has a title (`# ADR-NNNN: <title>`), a `Status:` line, a `Date:` line, and three sections:
  `## Context` (the forces and the problem), `## Decision` (what is chosen, stated so it can be
  checked) and `## Consequences` (what follows, good and bad). `Enforced by:` names the command,
  hook or review that keeps it.
- An ADR is written with `ape decision new <slug>`, which gives it the next number and the status
  `proposed`. Planning (`apex-plan`, `apex-change`) proposes one whenever it makes a binding choice;
  a person may write one too.
- A person accepts it (`ape decision accept ADR-NNNN`, or by typing **accept ADR-NNNN** to the
  operator). From then on its text is fixed: `ape project check` fails if anything but its
  `Status:` line changes.
- An accepted decision changes only by a new ADR that supersedes it
  (`ape decision new <slug> --supersedes ADR-NNNN`). The old one stays, marked
  `superseded by ADR-MMMM`, so the history of the choice is kept.
- Changes and requirements name the decisions they follow (`decisions:` in a change, `Decisions:` in
  a requirement), and review checks that a change follows every accepted decision or plans its
  replacement.

## Consequences

- Anyone, person or model, can find what binds the project and why, in one folder.
- A choice cannot drift silently: changing it takes a new record and a person's acceptance.
- Small choices that bind nothing beyond one change stay out of `development/decisions/`; they
  belong in that change's notes.
- This record is APEX's standard, the same in every project. `ape framework update` replaces it, in
  its own commit, when a release changes the standard; nobody edits it by hand. A project that wants
  a different rule supersedes it with its own ADR, and updates then leave it alone.

Enforced by: `ape project check` (accepted text held), `ape decision accept` (a person's act),
review (changes follow accepted decisions)
