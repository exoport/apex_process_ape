# `_apex/framework.yaml` reference

`_apex/framework.yaml` records which framework release is installed in the project, by which ape, what was copied, and which upgrade migrations have run. `ape framework setup` writes it and `ape framework update` rewrites it; `ape framework status`, `ape doctor` and the migration runner read it. Commit it, so every checkout agrees on the installed release and the migration ledger.

The file is regenerated on every install. Do not edit it by hand: the next install overwrites it, carrying forward only the migration ledger and what setup recorded.

## Example: an APEX v1 install

What `ape framework setup` writes for an APEX v1 release:

```yaml
# Generated by 'ape framework update'. Edits to this file will be
# overwritten on the next run. Track in git so all collaborators agree
# on which framework version is installed.
config_schema_version: "1"
installed_at: 2026-10-21T14:50:16.346108242Z
framework:
    repo_origin: https://github.com/exoar/apex_process_framework.git
    source: tag
    version_tag: v1.0.0
    git_hash: <the full 40-character sha v1.0.0 named>
    git_branch: ""
ape:
    version: 1.0.0
sources:
    skills:
        count: 9
        paths:
            - .claude/skills/apex-accept
            - .claude/skills/apex-apply
            - .claude/skills/apex-change
            - .claude/skills/apex-handoff
            - .claude/skills/apex-loop
            - .claude/skills/apex-orchestrator
            - .claude/skills/apex-plan
            - .claude/skills/apex-release
            - .claude/skills/apex-review
    pipelines:
        count: 0
        paths: []
    config:
        seeded: false
    config_local_example:
        seeded: false
    operating_rules:
        managed: false
```

A fresh install has no `migrations` list: setup runs no migration, and the ledger gains a row only when `ape framework update` applies one. It has no `governance` block unless the update synced a governance clone.

## Example: the ledger and the governance record

A v0 project lifted to v1 by `ape framework update` keeps its v0 ledger rows and adds the v1 entries the update ran. When the update synced a governance clone, it records which release:

```yaml
governance:
    repo_origin: https://github.com/exoar/apex_process_governance.git
    version_tag: v0.1.2
    git_hash: <the full sha v0.1.2 named>
# …
migrations:
    - id: v0.27.0_seq-01
      version: 0.27.0
      applied_at: "20261003101532"
    - id: v1.0.0_seq-01
      version: 1.0.0
      applied_at: "20261021150210"
```

## Top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `config_schema_version` | string | This file's schema. Currently `"1"`. Bumped only on a non-additive shape change. |
| `installed_at` | timestamp | RFC 3339 time of the last setup or update that changed the install. An update that changes nothing keeps it. |
| `framework` | object | The framework release installed. See [`framework`](#framework). |
| `governance` | object | The governance clone the last update synced. Absent when the project has none, or it was not synced. See [`governance`](#governance). |
| `ape` | object | The ape that performed the install. See [`ape`](#ape). |
| `sources` | object | What was installed. See [`sources`](#sources). |
| `migrations` | array | The applied-migration ledger, oldest first. Absent when no migration has been applied. See [`migrations`](#migrations). |

## `framework`

| Field | Type | Description |
| --- | --- | --- |
| `repo_origin` | string | The URL the framework clone is configured with (`git config remote.origin.url`), not a machine's `insteadOf` rewrite of it. Empty when the clone has no `origin`. |
| `source` | string | `tag`: a release, exported from its tag (the default). `worktree`: the clone's working tree (`--from-worktree`). |
| `version_tag` | string | `source: tag`: the release tag installed. `source: worktree`: HEAD's exact tag, empty when HEAD is not on a tagged commit. |
| `git_hash` | string | The full commit SHA installed: for `source: tag`, the commit the tag named at install time. If the tag later names another commit, `update`, `status` and `ape doctor` (`framework.tag_moved`) report it. |
| `git_branch` | string | `source: worktree`: the clone's branch, almost always `main`. Empty for `source: tag`. |

## `governance`

Present when the update synced a governance clone: `governance_repository_path` (in `_apex/config.local.yaml` or `_apex/config.yaml`), else `$APEX_GOVERNANCE_REPO`, else ape's own clone of `governance_repository_url`. A record of which canon the update synced, not a pin: any project's update on the machine moves the clone. See [The framework and governance clones are caches](../explanation/framework-and-governance-clones.md).

| Field | Type | Description |
| --- | --- | --- |
| `repo_origin` | string | The URL the governance clone is configured with, as for `framework.repo_origin`. |
| `version_tag` | string | The governance release the clone was brought to. Omitted when the clone has no release tag. |
| `git_hash` | string | The commit the clone was at. Omitted when unknown. |

A governance path that is a directory but not a git clone is read as it is and leaves no `governance` block.

## `ape`

| Field | Type | Description |
| --- | --- | --- |
| `version` | string | The version of the ape that performed the install. Not the framework's version: the two are released separately. `dev` for a binary built without release ldflags. |

## `sources`

What the install copied. Paths recorded here are expected to exist on disk; `ape framework status` reports a missing one as drift.

### `sources.skills`

| Field | Type | Description |
| --- | --- | --- |
| `count` | integer | Number of skill directories installed. |
| `paths` | array of string | Project-relative paths of the installed `apex-*` skill directories. Sorted. |

### `sources.pipelines`

| Field | Type | Description |
| --- | --- | --- |
| `count` | integer | Number of pipeline files installed. `0` for an APEX v1 release, which ships none. |
| `paths` | array of string | Project-relative paths of the installed pipeline files. Sorted. |

### `sources.config`

An APEX v1 install records `seeded: false`: `ape project init` writes `_apex/config.yaml`, not setup.

| Field | Type | Description |
| --- | --- | --- |
| `seeded` | boolean | `true` when setup wrote `_apex/config.yaml` (APEX v0 releases only). |
| `project_name` | string | APEX v0: the `project_name` setup seeded. Omitted when `seeded: false`. |
| `extensions` | array of string | APEX v0: the extensions setup seeded. Omitted when `seeded: false`. |

### `sources.config_local_example`

| Field | Type | Description |
| --- | --- | --- |
| `seeded` | boolean | APEX v0: `true` when setup wrote `_apex/config.local.example.yaml`. |

### `sources.operating_rules`

| Field | Type | Description |
| --- | --- | --- |
| `managed` | boolean | APEX v0: `true` when the install manages `_apex/apex-operating-rules.md` and the `CLAUDE.md` managed block. Always `false` for an APEX v1 release, which ships no operating rules. |

## `migrations`

The ledger of the framework's upgrade migrations (`_apex/migrations/*.md`) that `ape framework update` has applied: one row per entry, in the order they ran. It is a list rather than a set because "which migrations ran, and in what order" is what you ask when one half-applies. It is what makes a second update a no-op and a failed one resumable. See [The framework's upgrade migrations](../how-to/framework-update.md#the-frameworks-upgrade-migrations).

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | The entry's `id:`, such as `v1.0.0_seq-01`. |
| `version` | string | The entry's `version:`, the framework version that introduced it. |
| `applied_at` | string | When it was applied, as `YYYYMMDDHHMMSS` local time. |

- A row is added only for an entry the update ran and that succeeded. An entry whose check says the project already has its shape is reported as applied, but gets no row: ape never records work it did not do.
- The ledger is carried forward on every install. Installing an APEX v1 release removes the project's `v0.*` entry files, but their ledger rows stay.

## Contract for downstream tooling

Tools that read `framework.yaml` can rely on:

1. The file's existence as the signal that the framework is installed.
2. `framework.git_hash` as the canonical identifier of the installed release: `version_tag` can be empty.
3. `installed_at` as the time the install last changed. It does not advance on an update that changes nothing.
4. `sources.*.paths` as the record of what was installed. A path missing on disk is a local deletion; a path on disk but not in the list is a local addition.
5. `migrations` as the order in which the upgrade entries ran.
